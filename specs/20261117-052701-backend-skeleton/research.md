# Research: 2단계 백엔드 뼈대

- 날짜: 2026-11-18 초안, 같은 날 사용자가 spec '사용자 확인 필요' 20개를 추천값으로 정함. 2026-11-19 goldfish 리뷰 지적을 반영함
- 기준: 기획 문서(Claude Docs '킹고 컴패니언 새 기획', 저장소 밖, <https://claude.ai/artifact/Uy7CZF95K2SLR5ugXNuhmK>)의 '서버와 데이터' 절이 정한 기술(TypeScript, Postgres + pgvector, Ollama, Docker로 묶음, 학교 데스크톱 Ubuntu)과 1단계 코드(main `19daf15`의 `etl/`)
- 서버의 새 의존성은 `postgres`(DB 드라이버) 하나다. 운영자 화면(R17)은 3단계 학생 앱이 쓸 `@astryxdesign/core`를 먼저 들인다.
- 명령은 모두 `node server/cli.ts <명령>`이다([contracts/cli.md](contracts/cli.md)).

## R1. 실행 환경

- **결정**: Node 22.18 이상. TypeScript를 빌드하지 않고 Node의 타입 제거로 바로 돌린다(1단계 `node etl/notices/run.ts`와 같음). ESM. 타입 제거로 되는 문법만 쓴다(enum·namespace·매개변수 속성 없음). Docker 이미지는 `.nvmrc`와 같은 판(`node:22-slim`)이다.
- **이유**: 1단계가 이미 이 방식이라 빌드 단계와 설정이 늘지 않는다. CI는 `.nvmrc`(22)로 돌고 개발 맥은 v26이라, 둘 다에서 도는 문법과 API만 쓴다.
- **후속**: `.nvmrc`와 이미지의 Node를 함께 올리는 일(24나 26)은 이 기능 밖이다.
- **대안**: `tsc` 빌드(단계가 하나 늘어남), Bun·Deno(1단계 코드와 실행기가 달라짐).

## R2. HTTP

- **결정**: `node:http`와 작은 경로 표 하나를 쓴다. 경로는 `/api/notices/:id` 꼴로 적고, 조각을 나눠 맞춰 보는 함수(20줄 안팎)가 `:이름` 자리를 꺼낸다. 프레임워크는 쓰지 않는다. JSON 본문 읽기(64KB까지), 쿠키 읽기, 오류 응답, 로그인 확인, 운영자 확인은 `server/http.ts` 한 파일이다.
- **이유**: 경로는 40개 안팎이고 앞에 거는 확인은 로그인과 운영자 둘뿐이다. 전역 `URLPattern`은 Node 23.8부터라 CI(22)에 없다(2026-11-18 확인: 맥 v26.4.0에는 있고 `.nvmrc`는 22).
- **대안**: Hono(작지만 Node 어댑터까지 의존성 2개), Fastify(플러그인 체계가 이 규모에 큼), Express(오래되고 타입이 약함), `.nvmrc`를 올려 `URLPattern`을 씀(저장소 전체의 CI 실행기가 바뀌는 일이라 따로 한다).

## R3. DB와 벡터

- **결정**: Postgres 17 + pgvector(이미지 `pgvector/pgvector:pg17`). 드라이버는 `postgres`(porsager, 하위 의존성 0). 벡터는 `vector(1024)` 칸에 `'[…]'::vector` 글로 넣고, 유사도는 코사인 거리 `<=>`로 잰다. 공지 3,000건까지는 색인 없이 전부 비교한다. 1만 건을 넘으면 HNSW 색인을 더한다.
- **이유**: Postgres 클라이언트는 표준에 없다. `postgres`는 의존성이 없고, 태그드 템플릿이 값을 자리표시자로 넘겨 SQL 주입을 막는다. `sql.begin`으로 넣기를 한 트랜잭션에서 바꾼다(FR-002의 '반쯤 바뀐 자료가 보이지 않음').
- **대안**: `pg`(하위 의존성 여럿), ORM(Drizzle·Prisma: 스키마를 두 번 적음), pgvector npm 패키지(글 변환 한 줄이면 됨).

## R4. 스키마 바꾸기

- **결정**: `server/db/migrations/NNN_이름.sql`을 번호 순서로 한 번씩 적용하는 작은 명령을 둔다. 적용한 이름은 `schema_migrations` 표에 남긴다. 되돌리기 파일은 두지 않고 백업으로 되살린다(R15).
- **대안**: node-pg-migrate, Drizzle Kit(의존성).

## R5. 비밀번호와 로그인 유지

- **결정**:
  - 비밀번호는 `node:crypto`의 scrypt(N=2^15, r=8, p=1, 솔트 16바이트)로 바꿔 저장하고 `timingSafeEqual`로 비교한다.
  - 로그인 유지는 32바이트 무작위 토큰을 HttpOnly·SameSite=Lax 쿠키로 준다. 운영 모드는 Secure도 붙인다. DB에는 토큰의 SHA-256만 둔다.
  - 마지막으로 쓴 때부터 30일이다(FR-013). 쓸 때마다 늘리되 DB에는 하루에 한 번만 적는다. 로그아웃은 그 행을 지운다.
  - 상태를 바꾸는 요청은 `Content-Type: application/json`과 같은 출처의 `Origin`을 요구한다. 다른 사이트의 폼이 대신 보내지 못하게 하려는 것이다.
  - 5번 잇달아 틀리면 15분 잠근다(FR-011). 실패 수와 잠금이 끝나는 때는 로그인 수단 행에 둔다. 잠금이 끝난 뒤 첫 시도에서 실패 수를 0으로 돌리고 센다. 맞으면 0이다.
  - 개발 계정의 비밀번호는 8자 이상이다. 명령이 표준 입력으로 받아 명령 기록에 남지 않는다.
- **대안**: bcrypt·argon2(네이티브 의존성), JWT(로그아웃해도 바로 끝나지 않아 FR-013과 맞지 않음).

## R6. 로그인 방식 바꿔 끼우기

- **결정**: 로그인 방식은 `{ kind, verify(input) → subject | null }` 꼴이다. 2단계에 있는 방식은 개발 로그인(`dev`, 이메일·비밀번호)과 시험 안에만 있는 `test` 둘이다(spec US2-8). 학생 자료는 `students.id`에 붙고, `login_methods(kind, subject)`가 그 학생을 가리킨다(FR-009). 학교 전산이 방식(SAML·OIDC 등)을 알려 주면 `sso`를 더한다. 방식을 더하거나 빼도 학생 자료와 다른 기능은 그대로다(FR-010).
- 운영 모드에서 켜진 방식이 없으면 서버는 시작하지 않는다(FR-012). 운영 모드의 로그인은 HTTPS 뒤에서만 받는다(리버스 프록시가 `X-Forwarded-Proto: https`를 줄 때만. 아니면 403 `https_required`).

## R7. 모델 서버와 부하 제한 하나

- **결정**:
  - 모델 서버는 분류기와 같은 Ollama 하나다. 판정은 gemma4:12b, 임베딩은 bge-m3이다. 가장 추천과 흐름도 처음에는 gemma4:12b를 써서 메모리에 모델을 하나만 올린다.
  - 1단계의 `createThrottle`(답마다 그 시간의 1/4을 쉼, 온도에 가장 크게 오른 폭을 더해 80°C 이상이면 기다림)과 `readTemp`(리눅스는 thermal zone, 없으면 `sensors -j`)를 그대로 가져다 쓴다.
  - 프로세스 사이의 '한 번에 하나'(FR-044)는 Postgres advisory lock으로 지킨다. 연결 하나를 따로 잡아(`sql.reserve()`) 모델 요청 하나와 그 뒤 쉼 동안 세션 잠금을 걸고 놓는다. 연결이 끊기면 잠금도 풀려 죽은 프로세스가 잠금을 쥐고 있지 않는다. 매일 작업은 분류기 단계 내내 같은 잠금을 잡고 분류기를 자식 프로세스로 돌린다. 분류기 코드는 고치지 않는다. Ollama에도 `OLLAMA_NUM_PARALLEL=1`을 둔다.
  - 온도를 읽지 못하면 그 작업이 끝날 때까지 모델 요청을 보내지 않고 규칙으로 고른다.
- **부하 제한의 수명**: 1단계 `createThrottle`은 '실행 하나에 하나'로 만들었다(오름폭은 0에서 시작하고, 온도를 한 번 못 읽으면 그 뒤 요청을 모두 막는다). 오래 도는 서버에서는 이렇게 쓴다.
  - `server/model.ts`의 `openModel()`이 부하 제한 하나와 모델 요청 함수(`chat`, `embed`)를 묶어 돌려준다. `close()`는 `stop()`의 요약을 `model_bursts` 표에 한 줄 남긴다(요청이 0이면 남기지 않는다).
  - 매일 작업(jobs 프로세스)과 `ingest` 명령은 실행 하나에 하나를 연다(흐름 쓰기, 넣기의 벡터 만들기). 넣기는 `embed` 함수를 받아 써서, `server/model.ts`가 생기기 전(넣기 단계)에는 `createThrottle` 문을 넣은 `makeEmbed`를, 그 뒤에는 `openModel()`의 `embed`를 받는다(tasks T021, T054b). 분류기는 자식 프로세스라 제 부하 제한을 쓴다.
  - 다시 고르기 일꾼(api 프로세스)은 줄에 일이 생기면 하나를 열어 줄이 빌 때까지 잇달아 쓰고, 줄이 비면 닫는다. 잇단 요청 사이에 오름폭이 이어지므로 1단계의 한 실행과 같다. 닫힌 뒤의 다음 일은 새로 연다(쉬는 동안 식었으므로 오름폭을 0부터 다시 잰다).
  - 온도를 읽지 못해 문이 닫히면(`before()`가 false) 그 다시 고르기만 규칙으로 고르고, 그 일이 끝나면 닫는다. 다음 일은 새 부하 제한으로 센서를 다시 읽어 본다(FR-044의 '그 다시 고르기가 끝날 때까지').
  - 5초 표본 기록의 자리(`logDir`)는 1단계와 같은 `etl/.cache/load`다. api 컨테이너에는 볼륨을 붙이지 않아 컨테이너와 함께 사라지고, 요약만 `model_bursts`에 남는다.
- **잠금 키**: `pg_advisory_lock(hashtext('kingo:model:' || current_schema()))`. 운영은 스키마가 하나(`public`)라 모든 프로세스가 같은 키를 다투고, 시험은 파일마다 스키마가 달라 서로 막지 않는다(R19).
- **모델 이름**: 1단계와 같은 `KINGO_LLM_MODEL`(없으면 `etl/notices/llm.ts`의 `DEFAULT_MODEL`)이다. 요청의 꼴은 [contracts/llm.md](contracts/llm.md)다.
- **측정 작업**: GPU 없이 CPU로 gemma4:12b의 가장 추천 한 번이 1분을 넘으면, 학교 데스크톱에서 작은 모델과 비교해 고른다. 이 결과는 구현 중에 research에 더한다.
- **대안**: 파일 잠금(컨테이너 사이 공유 볼륨이 필요), 큐 서버 Redis(서비스와 의존성이 하나씩 늘어남).

## R8. 가장 추천 계산

- **규칙 점수**(FR-033b의 무게): 정수 합이고 무작위가 없어 같은 자료면 늘 같은 순서다.

  | 조건 | 점수 |
  |---|---|
  | 핵심 분야가 고른 분야 또는 '관심 있어요가 몰린 분야'와 맞음 | +40 |
  | 관련 분야만 맞음 | +20 |
  | 핵심 분야가 '관심 없음이 몰린 분야' | −60(분야가 안 맞는 공지보다 뒤에 섬) |
  | 진로 목표에 맞는 종류(FR-033 표, 채용은 3학년 이상) | +20 |
  | 벡터가 가까움: 프롬프트·관심 있어요 공지·고른 분야 벡터의 평균과 코사인 유사도 s | +round(20 × max(0, s − 0.3) / 0.7) |
  | 마감이 14일 안: 남은 날 d | +round(10 × (14 − d) / 14) |

  점수가 같으면 닫히는 날 가까운 순(마감 없는 공지는 게시일+30일인 닫히는 날로 센다), 그다음 게시 최근 순, 그다음 글 번호 큰 순이다. 분야가 붙지 않은 공지(`field_state`가 `off`·`missing`)는 분야 점수가 0이다(FR-040). 뺀 줄과 꺼진 분석의 몰린 분야는 쓰지 않는다.
- **학생 벡터**: 세 묶음(프롬프트 벡터, 관심 있어요 공지 벡터들의 평균, 고른 분야 벡터들의 평균)을 저마다 길이 1로 맞춘 뒤, 있는 묶음끼리 평균한다. 묶음이 하나도 없으면 벡터 점수는 0이다.
- **분야 판정 없음**(FR-040): 열린 공지 가운데 `field_state`가 `judged`나 `human`인 것이 하나도 없을 때다. 그때 관심 분야 선반은 `no_field_verdicts`로 빈다. 운영자가 한 공지에 분야를 넣으면(`human`) 그 공지는 분야 점수를 받고 선반에도 나온다. 몰린 분야 줄은 분야가 붙은 공지의 행동만 센다.
- **비슷한 공지 선반**(FR-039): 열린 공지마다 관심 있어요 공지들과의 코사인 유사도 가운데 가장 큰 값으로 줄을 세운다(관심 있어요 공지 자신과 숨길 공지는 뺀다).
- **LLM 고르기**: Ollama `format`(JSON 스키마)으로 `{ pick: 1~10, reason, cited: [] }`를 받는다. FR-035 검사를 통과하지 못하면 규칙 1위와 규칙 문장을 쓴다. 지시문 판은 1단계처럼 지시문의 해시로 정해 가장 추천에 남긴다. 요청 몸통, 지시문 뼈대, 답 검사 표는 [contracts/llm.md](contracts/llm.md)에 있다.
- **LLM에 넣는 것**(FR-034): 추천 후보 10개(제목, 주최, 종류, 마감, 분야), 처음 답, 고른 분야 이름, 프롬프트, 뺀 줄을 뺀 지금 판의 나의 분석 전체. 분석이 꺼진 학생은 나의 분석 없이 고른다.
- **규칙 문장**: 맞은 조건을 점수가 큰 순서로 두 개까지 잇는다(점수가 같으면 아래 표의 순서. 핵심 분야가 고른 분야와 몰린 분야에 모두 맞으면 '고른 분야' 조각 하나만 쓴다. 마감 조건은 점수가 1 이상일 때만, 즉 남은 날 13일 이하). 앞 조각은 '~고' 꼴, 끝 조각은 '~요' 꼴이다(예: '고른 분야와 맞고 마감이 가까워요'). 하나만 맞으면 끝 꼴 하나다. 날짜와 남은 날 수는 쓰지 않는다(가장 추천은 다음 다시 고르기까지 그대로 보여, 날 수를 적으면 낡는다. 마감은 카드에 따로 나온다).

  | 맞은 조건 | 앞 조각 | 끝 조각 |
  |---|---|---|
  | 핵심 분야가 고른 분야와 맞음 | 고른 분야와 맞고 | 고른 분야와 맞아요 |
  | 핵심 분야가 관심 있어요가 몰린 분야와 맞음 | 관심 있어요가 몰린 분야와 맞고 | 관심 있어요가 몰린 분야와 맞아요 |
  | 관련 분야만 맞음 | 고른 분야와 관련이 있고 | 고른 분야와 관련이 있어요 |
  | 진로 목표에 맞는 종류 | 진로 목표에 맞는 종류이고 | 진로 목표에 맞는 종류예요 |
  | 벡터 점수가 10 이상 | 관심 있어 한 것과 비슷하고 | 관심 있어 한 것과 비슷해요 |
  | 마감이 14일 안 | 마감이 가깝고 | 마감이 가까워요 |
  | 맞은 조건이 없음 | | 지금 열려 있는 공지 가운데 골랐어요 |

## R9. 다시 고르기 줄

- **결정**: `repick_queue` 표(학생마다 한 행)와 API 프로세스 안의 일꾼 하나. 일꾼은 2초마다 가장 오래된 행 하나를 집어(지우지 않는다) 모델 잠금 안에서 계산한다. 계산이 끝나면 `queued_at`이 집었을 때와 같을 때만 행을 지운다(계산 중에 다시 걸리면 남아 한 번 더 고른다). 다시 걸리면 `queued_at`과 `cause`를 새로 적는다. 계산이 던지면 기록하고 행을 둔다(다음 차례에 다시 해 본다). `cause`는 `daily`·`answers`·`fields`·`action`·`prompt`·`analysis`·`ingest`다. 같은 학생은 한 행이라 밀린 다시 고르기가 하나로 합쳐진다(FR-037). 매일 작업은 모든 학생을 넣는다. 홈의 '새로 고르는 중'은 이 줄에 그 학생 행이 있다는 뜻이다.
- **프롬프트 벡터**: `PUT /api/me/prompt`는 모델을 부르지 않는다. 글을 쓰고 벡터를 비운 뒤 다시 고르기 줄에 넣는다(모델 요청은 잠금과 온도 대기로 오래 걸릴 수 있어 앱 요청에 넣지 않는다, SC-007). 일꾼이 그 학생의 차례에 벡터가 비어 있으면 먼저 만들어 채우고 고른다. 임베딩이 실패하면 비운 채로 나머지 벡터만으로 고르고, 다음 차례에 다시 해 본다. 매일 작업이 모든 학생을 줄에 넣으므로 빈 벡터는 늦어도 다음 날 다시 만들어진다.
- **대안**: 메모리 큐(재시작하면 잃음), LISTEN/NOTIFY(더 복잡함).

## R10. 나의 분석 쓰기

- **사실 칸**(FR-032a): 재료를 바꾸는 요청과 같은 트랜잭션에서 다시 쓴다. 줄 목록(jsonb)에서 md를 만들고, md가 실제로 바뀔 때만 판 번호를 올린다. 판이 오르면 다시 고르기 줄에 넣는다.
- **매일 다시 쓰기**: 몰린 분야는 날짜(최근 30일, 이번 학기)와 공지의 분야(넣기, 운영자 고치기)에 따라 학생이 아무것도 하지 않아도 바뀐다. 그래서 매일 작업이 넣기 뒤에 모든 학생의 사실 칸을 한 번 다시 쓴다(규칙이라 모델을 부르지 않는다). 여기서 판이 오른 학생이 FR-043의 '사실 칸이 바뀐 학생'이다.
- **줄 키**(FR-029): 직접 넣은 활동 `act:<번호>`, 처음 답 `ans`, 고른 분야 `picked`, 몰린 분야 `liked:<분야 id>`·`disliked:<분야 id>`, 흐름 `flow:<근거 키를 정렬해 '+'로 이은 것>`. 흐름 키를 근거로 만들어서, 학생이 뺀 흐름과 근거가 같은 문장은 다음에도 빠진다(FR-032b). 근거가 같은 흐름 문장이 둘이면 앞의 것만 쓴다.
- **줄의 글과 출처**

  | 줄 | 칸 | 글의 틀 | 출처 | 증빙 |
  |---|---|---|---|---|
  | `act:<번호>` | 해 온 활동(`done`) | `<학기> · <이름> · <종류 이름> · <분야 이름, …>`(분야가 없으면 그 조각을 뺀다) | 직접 입력 | 증빙 링크 · 증빙 없음 |
  | `ans` | 관심 분야(`interest`) | `처음 답: <학년>학년 <학기>학기, <목표>`(4는 '4학년 이상', 목표는 취업·대학원·창업·아직 모름) | 처음 질문 | 없음 |
  | `picked` | 관심 분야 | `고른 분야: <이름, …>`(목록 순서) | 분야 고르기 | 없음 |
  | `liked:<id>` | 관심 분야 | `관심 있어요가 몰린 분야: <이름>` | 앱 기록 | 없음 |
  | `disliked:<id>` | 관심 분야 | `관심 없음이 몰린 분야: <이름>` | 앱 기록 | 없음 |
  | `flow:…` | 흐름(`flow`) | LLM이 쓴 문장 | 컴패니언 | 없음 |

  종류 이름은 분류기의 `KIND_LABEL`이다(해커톤, 대회·공모전 등).
- **md의 꼴**: 제목 `# 나의 분석` 아래 칸 셋이 이 순서로 온다. 줄은 `- <글> (<출처>[, <증빙>])`이고, 칸이 비면 `- 아직 없어요.` 한 줄이다. 줄 순서는 해 온 활동이 학기 최근 순(같으면 번호 순), 관심 분야가 위 표의 순서(몰린 분야는 목록 순서), 흐름이 받은 순서다. 뺀 줄은 넣지 않는다.

  ```md
  # 나의 분석

  ## 해 온 활동
  - 2025-2 · 교내 해커톤 · 해커톤 · 백엔드 (직접 입력, 증빙 없음)
  - 2025-1 · 오픈소스 기여 캠프 · 교육·캠프 (직접 입력, 증빙 링크)

  ## 관심 분야
  - 처음 답: 3학년 2학기, 취업 (처음 질문)
  - 고른 분야: 백엔드, 데이터베이스, LLM·생성형 AI (분야 고르기)
  - 관심 없음이 몰린 분야: 프론트엔드 (앱 기록)

  ## 컴패니언이 본 흐름
  - 아직 없어요.
  ```
- **몰린 분야**(FR-031): 카드 행동 표에서 계산한다. 관심 있어요는 최근 30일 안에 핵심 분야가 같은 공지 2번 이상, 관심 없음은 이유가 '관심 없는 분야예요'·'너무 어려워요'이고 이번 학기(3~8월, 9~2월) 안에 2번 이상이다.
- **흐름 정리**: 사실 칸을 다시 쓸 때 지금 없는 줄을 가리키는 흐름 문장을 함께 뺀다. 흐름을 쓴 뒤 `flow_version`은 흐름을 넣어 오른 뒤의 `version`이다(그래야 날마다 다시 쓰지 않는다).
- **흐름**(FR-032b): 매일 작업에서 분석 판이 지난 흐름의 판보다 높은 학생만 쓴다. LLM에는 사실 줄(키와 글)만 넣고 `{ lines: [{ text, refs }] }`를 받는다. 근거가 없거나 지금 없는 줄을 가리키는 문장, 80자를 넘는 문장, 학생이 뺀 흐름과 근거가 같은 문장은 버리고 앞에서 4줄까지 쓴다.

## R11. 넣기

- **결정**: 서버 명령 `ingest`가 한다. 순서는 다음과 같다.
  1. 결과 파일을 손으로 쓴 `checkResultFile`로 검사한다. 계약 스키마(`specs/20261107-193624-cse-notice-opportunities/contracts/cse-notices.schema.json`)의 규칙을 그대로 옮기고, 계약 시험이 규칙마다 맞는 예와 어긋난 예를 하나씩 본다.
  2. 분야 목록은 1단계 `checkTaxonomy`를 그대로 부른다.
  3. 벡터는 1단계 보관(`readNoticeVector`, `readFieldVectors`)에서 읽고, 없으면 `makeEmbed`와 1단계 글 규칙(`noticeText`, `fieldText`)으로 만든다. 본문은 분류기 보관본에서만 읽는다(`etl/notices/gold.ts`의 `cachedBody`: 학교 서버를 부르지 않는다). 벡터만 만들고 서버 DB에는 본문을 넣지 않는다(FR-006).
     - 넣는 벡터는 길이가 1024여야 한다. 1단계 보관은 모델 이름 폴더(`EMBED_MODEL`) 아래라 다른 모델의 벡터는 없는 것으로 읽힌다. 길이가 다른 벡터는 그 벡터만 넣지 않고 요약의 '못 만듦'에 센다(넣기 전체를 거절하지 않는다).
     - DB에 벡터가 없는 기회와 분야만 읽거나 만든다(이미 있으면 건드리지 않는다). 요약의 벡터 세 수(보관·새로·못 만듦)는 이번에 채우려 한 기회 공지만 센다(분야 벡터는 세지 않는다). 그래서 같은 파일을 다시 넣으면 세 수가 모두 0이다. 넣기가 만든 벡터는 1단계 `noticeVector`·`fieldVectors`로 만들어 분류기 보관에도 남긴다. 확인 필요 글은 벡터를 만들지 않고 `field_state`는 `off`다(이유는 `review:`만 붙는다). `--dry-run`은 모델을 부르지 않고 '새로 만들 수'만 센다.
     - 벡터만 채워진 공지는 '바뀜'이 아니라 '그대로'다.
  4. 한 트랜잭션에서 비교하고 쓴다. 사람 판정이 있는 칸은 결과 파일 값으로 덮지 않는다(FR-052).
  5. 요약을 남긴다(FR-007).
- **확인 필요 글**: 결과 파일의 `review` 줄도 `notices`에 넣되 `is_notice`가 거짓이다(종류·마감은 비어 있다). 학생 쪽 조회는 `is_notice`가 거짓인 공지를 내려간 공지와 똑같이 다룬다(목록·홈·가장 추천에서 빠지고, 행동이 남은 공지는 내 목록과 자세히에 `down` 표시로 보인다).
- **요약이 세는 것**: 새·바뀜·그대로는 이번 파일의 기회만 센다(DB에 공지로 없던 것, `file_hash`가 다른 것, 같은 것). 확인 필요 글은 '확인 필요 n'으로 따로 센다. 내려감은 기준일 안에 게시됐고 앞에는 파일에 있었는데(기회든 확인 필요든) 이번 파일에 없는 글이다. 기회였다가 확인 필요가 된 글은 `is_notice`가 거짓이 되고 '확인 필요'에만 센다(사람 판정 `is_notice`가 있으면 그 값을 둔다). 확인 필요였다가 기회가 된 글은 '새'다.
- **분야 목록**: 지금 분야 목록은 DB의 활성 목록(`taxonomies.active`)이다. `ingest --taxonomy <id>`는 그 목록 파일(`etl/taxonomy/<id>.json`)을 넣을 때마다 다시 읽어 판(edition)이나 내용이 바뀌었으면 고친다. 활성 목록이 없으면 그 목록이 활성이 된다. 활성 목록과 다른 id면 거절하고, `--switch`를 붙여야 갈아탄다. 갈아타면 한 트랜잭션에서 고른 분야를 모두 지우고(학생의 다음 할 일이 분야 고르기가 된다), 직접 넣은 활동의 분야와 사람 판정의 분야를 비우고(고친 기록에 남긴다), 몰린 분야 줄의 뺀 줄을 지우고, 공지 분야를 새 파일 값으로 쓴다. 결과 파일 머리의 목록 id는 `--taxonomy`와 같아야 한다(FR-003).
- **사라진 분야**: 같은 목록의 새 판에서 없어진 분야 id는 고른 분야, 직접 넣은 활동의 분야, 사람 판정의 분야, `liked:`·`disliked:` 뺀 줄에서 뺀다(FR-008).
- **확인할 것의 이유**(FR-050): `review:<분류기 이유>`(확인 필요 글), `no_deadline`(기회인데 마감 없음), `no_fields`(결과 파일에 분야 목록 머리가 있는데 그 기회에 분야 칸이 없거나 핵심·관련이 모두 빔). 결과 파일에 분야 목록 머리가 없으면(분야 판정이 꺼진 지금 같은 때) `no_fields`는 아무 글에도 붙지 않는다. 붙이면 모든 기회가 확인할 것에 들어가 쓸모가 없다.
- **다시 판정**(FR-054): 원문이 고쳐진 공지를 새로 받아 다시 묻게 하는 일이다. 매일 작업이 분류기를 돌리기 전에 표시된 공지의 분류기 보관 셋을 지운다: 본문 보관본(`CACHE_DIR/<글 번호>.html`), 기회 판정 보관 답(`LLM_CACHE_DIR/<modelDir(모델)>/<PROMPT_VERSION>/<글 번호>.json`), 분야 판정 보관 답(`fieldFolder(활성 목록, 모델)/<글 번호>.json`). 경로는 1단계 모듈이 내보내는 상수와 함수로 만든다. 분류기는 그 글의 본문을 다시 받아(요청 1건) 기회와 분야를 다시 묻는다. 요청이 `temperature: 0`이라 본문이 그대로면 답도 같다. 모델이나 지시문이 바뀐 때는 판이 바뀌어 모든 글이 다시 판정되므로 이 표시가 필요 없다.
- **대안**: JSON 스키마 검사기 ajv(의존성. 스키마가 단순해 손 검사로 충분하다).

## R13. 날짜

- **결정**: 날짜 계산은 모두 한국 시간이다. 1~2월은 앞 해의 2학기다(2027년 1월은 `2026-2`이고 그 학기 창은 2026년 9월 1일부터). 게시일·마감·다시 볼 날은 `date`, 사건 때는 `timestamptz`로 둔다. '오늘'은 `(now() at time zone 'Asia/Seoul')::date`다. 학기는 3~8월이 1학기, 9~2월이 2학기다.

## R14. 매일 작업

- **결정**: 호스트의 systemd timer가 03:00(한국 시간)에 `docker compose run --rm jobs node server/cli.ts daily`를 부른다. `Persistent=true`라서 그 시각에 꺼져 있었으면 켜진 뒤 한 번 돈다.
- **단계**(FR-043): 다시 판정 표시 처리(R11) → 분류기(모델 잠금 안, 자식 프로세스 `node etl/notices/run.ts`) → 넣기(DB의 활성 목록 id로. 활성 목록이 없으면 이 단계만 실패한다) → 백업 → 모든 학생의 사실 칸 다시 쓰기(R10) → 흐름 쓰기 → 모든 학생을 다시 고르기 줄에 넣기 → 줄이 빌 때까지 기다림 → 요약 저장. 분류기가 실패하면(끝 코드가 0이 아님) 넣기는 건너뛰고(`skipped`) 어제 자료로 다음 단계를 잇는다. 넣기가 실패해도 다음 단계를 잇는다.
- **기다림의 끝**: 줄이 비거나 그날 07:00이 되면 기다리기를 멈춘다. 남은 학생은 줄에 그대로 있고 api의 일꾼이 낮에도 이어서 한다(그동안 학생은 앞의 가장 추천이나 규칙 1위를 본다, FR-038). 07:00이 지나 손으로 돌린 실행은 줄에 넣기만 하고 기다리지 않는다.
- **요약 값의 출처**: 일꾼은 api 프로세스에 있으므로 매일 작업은 DB에서 센다. 다시 고른 수와 규칙 수는 줄에 넣은 때 이후 `picks.computed_at`이 바뀐 학생을 `method`로 나눠 세고, 남은 수는 `repick_queue`의 행 수다. 부하는 이 실행 동안의 `model_bursts`(R7)를 모아 낸다(최고 온도는 최댓값, GPU 평균은 요청 시간으로 무게를 준 평균). 분류기의 부하 줄은 자식 프로세스 표준 출력에서 `부하:`로 시작하는 줄이 있으면 그 줄이고, 없으면 비운다(실제 요청이 없던 날).
- **대안**: cron(꺼진 동안 놓친 실행을 잡지 못함), API 안의 타이머(재시작에 약함).

## R15. 백업

- **결정**: jobs 이미지에 서버와 같은 판의 클라이언트(postgresql-client-17)를 넣는다(판이 낮은 pg_dump는 거절된다). `pg_dump -Fc`를 같은 데스크톱의 두 번째 디스크(`/mnt/backup/kingo/`)에 `kingo-YYYY-MM-DD.dump`(한국 날짜)로 남긴다. 같은 날 다시 돌리면 덮어쓴다. 이름의 날짜가 오늘보다 7일 이상 앞선 파일을 지워 7개(오늘과 앞 6일)가 남는다. 이 꼴이 아닌 파일은 건드리지 않는다. 되살리기는 `pg_restore --clean --if-exists`이고, 대상 DB가 비어 있을 때만 한다(`students`와 `notices` 표가 없거나 둘 다 0행). 아니면 거절한다. 방법은 quickstart에 두고, 실제로 한 번 되살려 학생 자료 수를 비교한다(FR-046, SC-012).

## R16. 묶음과 네트워크

- **결정**: 학교 데스크톱 한 대의 Docker Compose 서비스 다섯이다(FR-041). 개발 맥에서는 DB만 `deploy/compose.dev.yaml`로 띄운다(아래).

  | 서비스 | 하는 일 | 네트워크 |
  |---|---|---|
  | db | Postgres + pgvector | inner |
  | ollama | 모델 서버(`OLLAMA_NUM_PARALLEL=1`) | inner |
  | api | 서버, 다시 고르기 일꾼, 운영자 화면 정적 파일 | inner |
  | proxy | 문지기(Caddy). 호스트의 8080을 열고 api로 넘긴다 | inner + outer |
  | jobs | 매일 작업과 분류기(학교 공지 서버에 1초 1건) | inner + outer |

- `inner`는 `internal: true`라 바깥 인터넷에 닿지 않는다. 학생 자료를 다루는 api와 db는 inner에만 있어서 바깥으로 연결을 열 수 없다(FR-042, SC-009를 네트워크가 막는다).
- **문지기가 있어야 하는 까닭**(2026-11-18 이 맥의 Docker 29.6에서 확인): internal 네트워크에만 붙은 컨테이너는 `ports`를 적어도 호스트에 열리지 않는다. 같은 실험에서 그 컨테이너는 바깥 주소에 닿지 못했고, 두 네트워크에 붙은 컨테이너는 포트가 열리고 inner의 컨테이너에도 닿았다. 그래서 포트는 proxy가 열고 api는 inner에만 둔다. proxy는 우리 코드가 없는 Caddy 이미지이고 설정은 `reverse_proxy api:8080` 한 줄이다. 3단계에서 같은 proxy가 HTTPS를 맡는다.
- **남는 틈**: jobs는 분류기 때문에 outer에도 붙어 있어 네트워크만으로는 바깥을 막지 못한다. 바깥으로 나가는 코드는 분류기의 학교 공지 요청 하나뿐이다. 서버 코드(`server/`)에는 `OLLAMA_HOST`가 아닌 곳으로 가는 요청이 없다는 것을 시험이 본다(SC-009).
- Ollama 모델은 처음 한 번, outer에 붙인 일회용 컨테이너(`ollama-pull`, 같은 볼륨)로 받는다.
- **이미지**: api와 jobs는 같은 이미지(`deploy/Dockerfile`)를 쓰고 명령만 다르다(api는 `node server/main.ts`). `node:22-slim`에 PGDG 저장소의 `postgresql-client-17`과 `lm-sensors`를 넣고, 저장소를 통째로 복사해(`.dockerignore`: `node_modules`, `.git`, `etl/.cache`, `etl/gold`, `etl/out`, `.env*`) `npm ci`(분류기가 `jsdom`을 쓰므로 dev 의존성까지)와 `npm run build:ops`를 돌린다.
- **볼륨**

  | 서비스 | 붙이는 것 |
  |---|---|
  | db | `db-data` → `/var/lib/postgresql/data` |
  | ollama, ollama-pull | `ollama-models` → `/root/.ollama` |
  | jobs | `etl-cache` → `/app/etl/.cache`(본문 보관본, LLM 보관 답, 벡터, 부하 기록), `etl-out` → `/app/etl/out`(결과 파일), 호스트의 `/mnt/backup/kingo` → `/backup`, 설정 파일(읽기 전용) |
  | api | 설정 파일(동의 문구, 운영자 목록)만 읽기 전용으로 |

  분류기는 보관 자리와 결과 파일을 코드 옆 고정 경로에 쓰므로(`etl/.cache`, `etl/out`) 그 경로에 볼륨을 붙인다. 붙이지 않으면 `--rm` 컨테이너가 끝날 때 사라져 밤마다 모두 다시 받는다.
- 개발 맥에서는 db만 Docker로 띄우고 서버와 Ollama는 맥에서 바로 돈다(Metal GPU). 개발 계정뿐이라 실제 학생 자료가 없다.
- **대안**: api를 두 네트워크에 붙임(바깥으로 나갈 수 있게 됨), 호스트 방화벽 규칙(관리자 권한과 손 설정이 필요하고 Docker가 규칙을 바꾼다).

## R17. 운영자 판정 검토 화면

- **결정**: `web/ops/` 폴더의 Vite + React PC 페이지 하나이고, 컴포넌트는 astryx(디자인 시스템 패키지 `@astryxdesign/core`, 0.7 판)를 쓴다. 사용자가 2026-11-18에 정한 화면 디자인 결정을 따른다: 화면은 astryx 컴포넌트로 바로 코드로 만들고(Figma에 다시 그리지 않는다), 강조색은 학교 홍보팀 확인 전이라 astryx 기본 테마를 쓴다. 3단계 학생 앱도 같은 패키지를 쓴다. `@astryxdesign/core`와 개발용 `@astryxdesign/cli`를 `package.json`에 더한다.
- **빌드와 주기**: `npm run build:ops`(`vite build --config web/ops/vite.config.ts`, `base: '/ops/'`)가 `web/ops/dist`에 쓴다. api가 그 폴더를 `/ops/`에서 준다(폴더가 없으면 404). `tsconfig.json`의 `include`에 `web`을 더하고 CI의 build 단계가 `build:ops`도 돌린다. 정적 파일에는 자료가 없어 로그인 없이 주고, 자료는 `/api/ops`가 운영자 확인 뒤에 준다. 페이지는 `/api/ops/review`가 `login_required`면 로그인 칸(개발 로그인)을, `forbidden`이면 '운영자 계정이 아니에요'를 보인다.
- **운영자 목록**: 설정 파일(`KINGO_OPERATORS_FILE`)에 로그인 수단과 역할을 둔다(FR-049). 꼴은 `{ "operators": [{ "kind": "dev", "subject": "ops@example.com", "role": "operator" }] }`이고 역할은 `operator`(운영자)와 `dept`(학과 담당자)다(2단계에서는 권한이 같다). 서버가 시작할 때 한 번 읽는다(바꾸면 다시 시작한다). 파일이 없으면 운영자가 없는 것이라 모든 ops 경로가 `forbidden`이다. 고친 기록의 `by_operator`에는 그 `subject` 글을 적는다(학생 번호를 적지 않는다).
- **사람 판정**: 공지와 칸마다 한 행이다. 학생에게 줄 때는 사람 판정이 있으면 그것을, 없으면 결과 파일 값을 쓴다.
- **정답셋 후보 내보내기**: `export-gold <폴더>`가 `<폴더>/gold-candidates-YYYY-MM-DD.csv`를 쓴다(칸은 [contracts/cli.md](contracts/cli.md)). 운영자가 고친 값은 정답 라벨이고, 정답셋은 사용자가 올리기로 정하기 전까지 공개 저장소에 두지 않으므로(스펙 1 FR-034) 저장소 안 경로는 거절한다(FR-053). 경로 검사는 `etl/notices/gold.ts`의 `insideRepo`를 내보내 쓴다.
- **대안**: 서버가 그리는 HTML 폼(빠르지만 3단계 앱과 따로 놀아 다시 만들게 됨).

## R18. 서버 기록

- **결정**: JSON 한 줄씩 표준 출력에 쓴다. 요청 기록에는 방법, 경로 틀, 상태, 걸린 시간, 학생 내부 번호만 남긴다. 요청 본문, 쿠키, 프롬프트, 분석 글, 활동 이름은 남기지 않는다(FR-047). 시험이 기록에 이것들이 없는지 본다.

## R19. 시험

- **결정**: 저장소 방식대로 vitest와 `*.test.ts`를 쓴다. DB가 필요한 시험은 진짜 Postgres(로컬 Docker, CI는 서비스 컨테이너 `pgvector/pgvector:pg17`)에서 시험 파일마다 새 스키마(`t_<무작위>`)를 만든다. 스키마로 나뉘지 않는 것이 둘 있다. (1) pgvector 확장은 DB에 하나라 `public` 스키마에 둔다(`create extension if not exists vector with schema public`). 시험 연결의 `search_path`는 `<시험 스키마>, public`이고, 여러 시험 파일이 함께 시작해도 부딪히지 않게 확장 만들기는 `pg_advisory_xact_lock` 안에서 한다. (2) 모델 잠금 키는 스키마 이름으로 만든다(R7). 모델은 1단계처럼 가짜 함수를 넣는다. 계약 시험은 contracts/api.md의 경로마다 되는 예 하나와 거절되는 예 하나를 본다. CI에 Postgres 서비스를 더한다.

## R20. 설정과 비밀

- **결정**: 설정은 환경 변수다. 비밀(운영 DB 비밀번호)은 `.env`에 두고 커밋하지 않는다(`.gitignore`가 막는다). 저장소에는 `.env.example`만 둔다(FR-048. `.gitignore`의 `.env.*`가 이것도 막으므로 `!.env.example`을 더한다).

  | 변수 | 기본값 | 뜻 |
  |---|---|---|
  | `KINGO_MODE` | 없음(필수. `dev`·`prod`가 아니면 시작하지 않는다) | 개발 모드와 운영 모드 |
  | `DATABASE_URL` | 없음(필수) | 개발 DB는 `postgres://kingo:kingo@127.0.0.1:54329/kingo`(`compose.dev.yaml`이 만드는 값) |
  | `PORT` | `8080` | api가 듣는 포트 |
  | `OLLAMA_HOST` | 1단계와 같음(`127.0.0.1:11434`) | 모델 서버 |
  | `KINGO_LLM_MODEL` | 1단계 `DEFAULT_MODEL`(gemma4:12b) | 가장 추천과 흐름의 모델 |
  | `KINGO_CONSENT_FILE` | 개발 모드 `deploy/consent.dev.md`, 운영 모드는 필수 | 동의 문구(R23) |
  | `KINGO_OPERATORS_FILE` | 없음(없으면 운영자 없음) | 운영자 목록(R17) |
  | `KINGO_BACKUP_DIR` | 없음(`backup`·`restore`·매일 작업의 백업 단계에 필수. 없으면 그 단계만 실패) | 백업 폴더 |
  | `KINGO_API_URL` | `http://127.0.0.1:8080` | `status`가 api의 `/api/health`를 부르는 주소(compose에서는 `http://proxy:8080`) |

- **읽는 법**: npm 스크립트가 `node --env-file-if-exists=.env`로 돌린다(`server`, `cli`). 시험은 `DATABASE_URL`이 없으면 개발 DB 주소를 쓰고, CI는 서비스 컨테이너의 주소를 환경 변수로 준다. 운영 값은 학교 데스크톱의 `deploy/.env`에만 둔다(compose의 `env_file`).
- 분류기의 보관 자리는 변수가 아니라 코드 옆 고정 경로다(R16의 볼륨).

## R22. 사람 판정과 학생에게 보이는 값

- **결정**: `notices` 표의 칸(공지 여부, 종류, 마감, 분야)은 학생에게 보이는 값이다. 결과 파일의 값은 그 줄 그대로 `file`(jsonb)에 두고, 사람 판정은 `human_verdicts`에 칸마다 둔다.
  - 넣기: 칸마다 사람 판정이 있으면 그 값, 없으면 결과 파일 값을 보이는 값에 쓴다(FR-052).
  - 운영자가 고침: 사람 판정을 쓰고 보이는 값을 바꾸고 고친 기록을 남긴다. 한 트랜잭션이다.
  - 닫히는 날(`closes_on`)은 보이는 마감으로 계산한다. 운영자가 마감을 고치면 열린 공지인지도 함께 바뀐다.
- **이유**: 학생 쪽 조회(목록, 홈, 선반, 가장 추천)가 한 표만 읽는다. 조회마다 사람 판정을 합치지 않아도 된다.
- **대안**: 조회할 때마다 `coalesce(사람 판정, 파일 값)`(모든 조회가 복잡해지고, 계산 칸 `closes_on`을 쓸 수 없다).

## R23. 동의 문구

- **결정**: 문구는 파일 하나(`KINGO_CONSENT_FILE`)에서 읽는다. 첫 줄이 판(`version: …`)이고 나머지가 글이다. 저장소에는 개발용 문구(`deploy/consent.dev.md`, 판 `dev-1`)만 둔다. 운영 모드는 판이 `dev-`로 시작하는 문구로는 시작하지 않는다(실제 문구는 학교 개인정보 담당 확인 뒤에 정한다, spec 사용자 확인 3번).
- 판이 바뀌면 앞 판에 동의한 학생의 다음 할 일이 다시 '동의'가 된다.
- 운영 모드가 `dev-` 문구로 시작하지 않는 것은 시작 검사 시험이 본다(tasks T027).
